- [spring-boot/spring-execution-contexts-and-hooks.md](spring-boot/spring-execution-contexts-and-hooks.md) — hook points beyond a single request's path: bean lifecycle callbacks (@PostConstruct/@PreDestroy, BeanPostProcessor), async/deferred execution (@Async, @Scheduled, message queues), event publishing (ApplicationEventPublisher, @TransactionalEventListener), transaction-boundary hooks, ambient context holders (RequestContextHolder in detail, SecurityContextHolder, MDC), context-scoped beans, a decision checklist for choosing between them, how uncaught exceptions are handled (or silently swallowed) in each one, and the centralized-handling mechanism that plays @ExceptionHandler's role per context (AsyncUncaughtExceptionHandler, ErrorHandler, Kafka's CommonErrorHandler, etc.).
- [spring-boot/spring-request-lifecycle.md](spring-boot/spring-request-lifecycle.md) — how an HTTP request flows through Tomcat, filters, DispatcherServlet, RequestBodyAdvice, interceptors, the controller, AOP proxies, service/repository layers, and back out via message converters and ResponseBodyAdvice, plus the exception-handling path (HandlerExceptionResolver, @ExceptionHandler resolution order) and supporting beans (HandlerAdapter, WebMvcConfigurer, Validator, ConversionService, ObjectMapper, CORS, async support).
- [spring-boot/sql-injection-protection.md](spring-boot/sql-injection-protection.md) — why Spring Boot has no dedicated anti-SQL-injection feature: protection comes from parameterized queries/prepared statements, which Spring Data JPA and JdbcTemplate generate automatically when used as intended (derived methods, `:name`/`?` placeholders, Criteria API); what a prepared statement actually is (raw JDBC prepare/bind/execute lifecycle, batch reuse, its distinct security vs. performance benefits); plus safe-vs-unsafe pattern tables (native queries, string concatenation, unbindable identifiers like column names).

- [system-design/idempotency.md](system-design/idempotency.md) — what idempotency means, where it shows up (HTTP methods, idempotency keys, at-least-once message delivery), the concrete mechanisms used to achieve it (dedup stores, conditional writes, unique constraints, inbox pattern), and client-generated vs server-issued keys with the "unused/consumed/unknown" three-state check needed to avoid re-processing or wrongly discarding retries.
- [system-design/load-balancing-l4-vs-l7.md](system-design/load-balancing-l4-vs-l7.md) — what a load balancer buys you (scale, availability, zero-downtime deploys, one stable address) and the L4/L7 split: L4 balances *connections* on IP+port with the payload sealed (protocol-agnostic, fastest, TLS passthrough, but no path routing, no retries, and it pins HTTP/2/gRPC to one backend) vs L7 balancing *requests* after parsing them (path/host/header routing, retries, canary, cookie stickiness, WAF — at the cost of CPU and holding your TLS keys), a sorting-facility vs receptionist analogy, balancing algorithms (round robin, least-connections/least-request, EWMA, P2C, consistent hashing), L4 vs L7 health checks and connection draining, sticky sessions, HAProxy `mode tcp` vs `mode http` config, why real stacks chain DNS → L4 → L7 → app (and how k8s Service vs Ingress maps to it), a decision checklist, and gotchas (client-IP loss and the PROXY protocol, timeout mismatches, 502s on deploy).
- [system-design/message-queue-vs-pubsub.md](system-design/message-queue-vs-pubsub.md) — message queues (one consumer per message) vs pub/sub (broadcast to all subscribers), where an event bus fits (usually pub/sub semantics plus content-based routing, in-process or distributed), and how Spring Boot's `ApplicationEventPublisher` (in-process pub/sub) compares to JMS (broker-backed queue or topic destinations).
- [system-design/monolith-vs-microservices.md](system-design/monolith-vs-microservices.md) — what "service" means (Order Service, Payment Service, etc.): independent processes/databases/deploy lifecycles talking over the network vs modules sharing one process in a monolith, plus a decision checklist for which to build.

- [system-design/rate-limiters.md](system-design/rate-limiters.md) — common rate limiting strategies (fixed window, sliding window log/counter, token bucket, leaky bucket) and Uber's distributed control-plane architecture (local probabilistic dropping instead of per-request Redis lookups).
- [system-design/redis-persistence-rdb-vs-aof.md](system-design/redis-persistence-rdb-vs-aof.md) — Redis persistence: RDB snapshots vs AOF write log, trade-offs and when to use each.
- [system-design/redis-single-threaded.md](system-design/redis-single-threaded.md) — how Redis works, why it's called single-threaded, why `INCR` is atomic, and use cases beyond caching.
- [system-design/rest-api-path-vs-query-params.md](system-design/rest-api-path-vs-query-params.md) — `/users/{id}` vs `/users?userId=xxx`: why path params are conventional for identifying one unique resource and query params for filtering/sorting/paging a collection, a postal-address analogy, and a decision checklist with GitHub/Stripe examples for each option.
- [system-design/reverse-proxy-protocol-termination.md](system-design/reverse-proxy-protocol-termination.md) — why the standard production shape is HTTP/2 (+TLS/HTTP/3) between browsers and the reverse proxy but plain HTTP/1.1 keep-alive between the proxy and the app: that a proxy is two independent connections (so each side's protocol is a separate choice), which HTTP/2 features only pay off on a high-RTT public network, why HTTP/2 to the backend can hot-spot one instance behind an L4 balancer, a shipping-port analogy, the gotchas (`X-Forwarded-*` and `server.forward-headers-strategy`, NGINX's HTTP/1.0-upstream default silently killing keep-alive, WebSocket/SSE, HTTP/3) with NGINX and Spring config, and a decision checklist for edge termination vs end-to-end HTTP/2 (gRPC, service mesh).
- [system-design/saga-pattern-compensating-transactions.md](system-design/saga-pattern-compensating-transactions.md) — the Saga pattern: handling a later step (e.g. payment) failing after an earlier step (e.g. order creation) already committed, via compensating transactions, orchestration vs choreography, how to decide between them, and idempotency.
- [system-design/scheduler-internals.md](system-design/scheduler-internals.md) — why schedulers don't poll every millisecond: the deadline-based sleep design (min-heap of next-fire-times, block until exactly the soonest one), timer wheels for millions of short-lived timers (Netty, Linux kernel, Kafka), hardware timer interrupts and tickless kernels, and how Spring's `@Scheduled` fits this model.
